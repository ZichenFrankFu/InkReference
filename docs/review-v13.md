# v13 仓库审查与后续缺口

审查以当前仓库的实际入口、导入关系、SQL、存储合同与验证记录为依据。下表的“缺口”不代表本轮已实现；修复结果以本轮最终提交和 [validation.md](validation.md) 为准。

## 本轮处理范围

| 问题 | 已落实的方向 | 仍保留的边界 |
|---|---|---|
| 动态功能交互各自实现 | 建立动态功能能力目录和共享三模式控件；业务适配器保留领域校验、后台任务和确认事务。 | 没有把所有业务压入一个通用 JSON 写库入口；历史合同与旧 API 独立兼容。 |
| 图标与桌面身份分散 | 单一蓝底白色 R 图源生成浏览器、Windows 与 macOS 图标；原生入口及打包资源使用同一身份。 | 浏览器模式的系统任务栏图标由浏览器管理；原生窗口、安装包首次打开仍需对应系统验收。 |
| 历史用量随请求整批反序列化 | 用量列表分页、数据库聚合及适用查询索引；保留完整逐请求台账。 | 聚合不是丢弃历史，用户调用数据仍会增长。 |
| 错误缺少跨模块定位 | 结构化日志、请求／任务／诊断 ID、源码帧、后台任务事件与快捷修复诊断连接。 | 不自动收集正文、提示词、密钥或请求内容；用户需提供复现动作。 |
| 已退场界面仍留源码 | 按导入图移除无入口的独立转换界面、旧文件／预处理面板及确认未用导出，保留后端兼容能力。 | 兼容数据路径、旧 Schema 和迁移测试不是冗余，继续保留。 |
| 文档与功能入口对应不足 | 完整 [使用手册](gui_manual.md)、[架构](architecture.md)、[API](api-contract.md)、[日志](logging.md) 与本报告互相链接。 | 文档不把合成模型测试写成真实模型质量评测。 |

## 优先补齐的能力

优先级以用户数据可靠性、长篇工作流和日常使用收益排序；代价是相对工程量，不是已承诺交期。

| 优先级 | 当前缺口与代码依据 | 用户影响 | 建议与代价 |
|---|---|---|---|
| P1 | 真实作品的模型质量及向量阈值未校准。`semantic_search.py` 使用固定 0.90／0.78 匹配阈值，现有自动化通过合成提供方验证协议和数据一致性。 | 同义桥段可能漏合并，相近但不同的剧情可能被建议复用；热度区间也不能当作全网实测。 | 建立人工标注的作品／桥段集，分别评估身份、事实证据、重复桥段和不同 embedding 模型；记录 Precision／Recall 与人工改动率。代价中。 |
| P1 | Windows／macOS 原生中文输入、窗口生命周期、任务栏图标和真实安装／首开尚需实机人工验收；冻结包 CI 主要验证本地 HTTP、资源和数据。 | 浏览器检查通过仍可能出现 IME、焦点、平台安全提示或图标缓存问题。 | 在两类 Mac 与 Windows 上运行固定验收单，保留系统版本、截图和复现日志。代价小至中。 |
| P1 | 长期数据容量仍有限：`reference_analysis.py` 的单份内容为 8,000,000 UTF-8 字节；`projects.py` 恢复包 512 MiB、展开内容 2 GiB。备份使用 `BytesIO`，并按文件 `read_bytes()`。 | 多本超长小说、分析历史和任务候选积累后，备份可能占较多内存或超过恢复上限。 | 将事实与版本按实体／贡献拆存并分页读取；采用流式 ZIP 或分卷备份，设计可恢复的格式升级。代价大。 |
| P1 | 删除素材直接执行有 revision 的事务删除；没有用户可浏览的回收站。备份为用户显式导出，没有定期自动备份策略。 | 用户确认后误删的现代素材只能依靠已有项目备份恢复；恢复整库也较重。 | 先实现有保留期的软删除与选择性恢复，再提供受容量限制的自动备份。历史正文版本与源码修复回滚继续各司其职。代价中。 |
| P2 | 搜索主要是 JSON 字段的 `instr(casefold(...))` 子串匹配；普通 B-tree 索引不能使任意中文子串检索变成索引查询。没有全局 FTS 全文检索。 | 大量作品、事件和章节积累后，跨库查找会变慢，且无法统一找“类似冲突／人物关系”。 | 先加中文可验证的 FTS／搜索投影和按作品限制，再设计跨作品事实检索。保留 ID 精确查找与现有子串行为。代价中至大。 |
| P2 | `semantic_search.py::match` 对所有现有候选做精确余弦计算并排序；向量缓存减少 API 请求，但不是 ANN 向量索引。 | 桥段数较大时，本地比较时间和首次 embedding 成本仍增长。 | 以真实规模测量后引入 SQLite 向量扩展或 ANN，保留目标指纹、精确复核和人工确认；按 embedding 版本重建。代价中。 |
| P2 | 正文更新后，`catalog_links.py` 可标记分析来源含旧版本；尚无按“源范围 → 贡献 → 派生事实”自动失效和局部重提的依赖图。现有范围复用只安全复用完全一致的完整块。 | 用户需决定哪些分析需要重提；编辑开头可能影响后文角色状态，不能只替换当前章结果。 | 增加变更区间与贡献依赖，先提供受影响事实预览，由用户选择重提，避免静默覆盖人工结果。代价大。 |
| P2 | 来源清单保留每次上传与原始字节，但 `studio.py` 没有删除某一上传来源并撤回其正文范围的接口。`text_processing.py` 对不可恢复乱码仅诊断，没有已验证的编码往返恢复。 | 误补充文件需要用历史恢复或逐章操作处理；部分可逆乱码也需要手工修复。 | 为逐来源撤回提供明确区间预览和新版本；编码恢复只处理可证明往返一致的候选，保留原文和人工确认，不能猜补缺字。代价中至大。 |
| P2 | 已有任务和阶段 token 预算，`workflows.py` 会在发送前检查；尚无跨资料搜索、分卷、修复和提取的按月／金额统一硬限额。 | 多功能、多模型并行时，单任务预算不足以约束总 API 支出。 | 统一预估、保留与结算机制，按币种显示预算；外部网页模型与搜索服务费用继续标未知。代价中。 |
| P2 | 完整项目备份逐个数据库生成快照；普通写入由单工作区和 idle 协调保护，但没有持续同步／云端协作协议。 | 多设备互拷数据目录不能安全当作多人协作。 | 当前使用项目 ZIP 迁移；若确需协作，另设计服务端冲突与版本协议，不把共享 SQLite 目录作为替代。代价大。 |
| P2 | macOS 包为 ad-hoc 签名，Windows 包无代码签名；`scripts/package.py` 清楚记录 `signed`／`notarized`。没有应用内自动升级流程。 | 普通分发可能出现系统拦截或来源提示；用户需要手动替换应用。 | 接入正式发布签名、公证、可验证更新清单与失败回滚。代价中，需发布者凭据。 |
| P3 | `Library.tsx` 和 `Jobs.tsx` 仍承载多类旧版兼容与工作区协调；工作区边界已分开，文件仍偏大。 | 修改入口时容易影响旧逻辑，后续开发阅读成本较高。 | 按独立领域组件拆分，优先用量、旧任务及表单；保留现有 API 和回归覆盖，不为缩短文件机械分层。代价中。 |

## 当前规模策略的实际含义

已具备 SQL 分页、适用索引、惰性页面、摘要与当前章读取、局部清洗重算、有限缓存、历史保留和模型块复用。它们降低普通打开页面时的成本，不能保证数据无限增长后始终保持相同耗时。

原始上传、受任务／审核引用的正文、任务候选、逐请求用量和稳定事实属于需要保留的业务记录，不通过“清缓存”自动删除。普通正文最近 10 版、章节读模型最近 3 版、分析恢复最近 10 次、有限向量／候选缓存与日志轮转有各自边界；被引用历史可超过普通保留上限。每次准备扩大上限或批量清理前，应先测量数据库大小、行数、查询计划及实际页面延时，并保留可验证备份。

## 验证边界

规则测试、实际 SQLite 事务、真实前后端浏览器流程、合成 HTTP 模型、真实 MinerU 文字层提取和真实模型推理分别记录。OCR、联网来源覆盖、模型推理准确率、真实 embedding 下载和系统原生交互不能相互替代。最终测试数量和 CI 以本轮 [validation.md](validation.md) 的记录为准，历史批次的数量不累计宣称为本轮执行结果。
